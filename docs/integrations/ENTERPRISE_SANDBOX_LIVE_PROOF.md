# Enterprise Sandbox Live Proof

## Purpose

The Enterprise Integration control plane must be able to prove a customer endpoint binding by crossing a real customer-owned **sandbox** boundary, not only by validating metadata.

A successful proof demonstrates the complete governed chain:

```text
Enterprise Settings
  -> declared Maestro task
  -> validated endpoint binding
  -> canonical task input
  -> request path/query/body mapping
  -> supervisor sandbox execution grant
  -> transient credential resolution
  -> public HTTPS destination guard
  -> real sandbox HTTP request
  -> bounded JSON response
  -> response-to-canonical mapping
  -> validated Task Injection Envelope
  -> declared task output slot
  -> redacted SHA-256 evidence
```

The proof is intentionally **not** a production connector approval.

## Bidirectional mapping contract

The endpoint contract separates both directions deliberately.

### Maestro to customer API

Path/query parameters and, for `POST` / `PUT` / `PATCH`, a dedicated request-body mapping transform canonical `$task.<field>` values into the customer's API shape. A write-capable sandbox binding cannot execute without a request-body mapping that covers every required canonical task field.

Example:

```text
Maestro canonical input
  subject                -> ticket.subject
  description            -> ticket.description
  customer_id            -> ticket.customer.id

Customer sandbox request JSON
  {"ticket": {"subject": "...", "description": "...", "customer": {"id": "..."}}}
```

### Customer API to Maestro

The response-data path selects the response object and field mapping transforms customer JSON paths into the exact canonical schema declared by the selected `IntegrationTaskCapability`.

A successful mapping is then validated again by the Task Injection contract before the proof can pass.

## Task Injection proof

A mapped API response is not considered sufficient on its own. The sandbox executor constructs a versioned Task Injection Envelope containing:

- `binding_id`;
- `task_id`;
- `adapter_contract_id`;
- operation class;
- exact required scopes;
- declared `output_slot`;
- canonical input digest;
- Task Injection digest;
- `ready_for_task_consumption=true`.

The envelope uses schema version `2026-08-enterprise-task-injection-v1`. Missing required canonical fields or fields outside the task schema fail closed. This proves that the retrieved sandbox data is not merely readable: it is structurally ready for the intended Maestro task boundary.

## Preconditions

A live sandbox proof requires:

1. an eligible Enterprise Integration entitlement;
2. a schema-valid endpoint binding;
3. a declared Maestro integration task and exact adapter scopes;
4. valid request mapping for methods that carry a JSON body;
5. a validated supervisor write session with `admin:integration:qualification:approve`;
6. a short-lived sandbox execution grant bound to `binding_id + task_id + operation_class + scopes`;
7. a deploy-time credential reference resolvable outside Settings;
8. an HTTPS destination whose DNS result contains only public addresses.

No raw credential value is accepted by the endpoint-binding or request-mapping Settings models.

## Credential boundary

The live proof resolver reads deployment-only sandbox variables derived from the credential profile identifier:

```text
MAESTRO_SANDBOX_AUTHORIZATION_<PROFILE>
MAESTRO_SANDBOX_API_KEY_<PROFILE>
```

The value is transient. It is not written to Settings, the binding store, the request mapping, the grant, the evidence record, logs generated by this capability, or the API response.

This environment-backed resolver is a sandbox deployment mechanism. Production qualification requires a customer-specific vault/secret-manager reference resolver rather than a profile-wide environment reference.

## Network controls

The governed sandbox execution path:

- requires HTTPS;
- rejects localhost/local/metadata targets at binding validation;
- resolves the hostname before credential resolution and rejects private, loopback, link-local, multicast, reserved, or unspecified addresses;
- disables environment proxy inheritance;
- disables redirect following and rejects redirect responses;
- enforces the binding timeout;
- caps the response body at 1 MiB;
- accepts JSON responses only;
- requires an explicitly allowed success status;
- never includes credentials in request previews or proof evidence.

The current DNS check is a pre-connect destination guard. Production qualification must additionally use transport-level destination pinning or verified peer-address enforcement to remove DNS rebinding/TOCTOU ambiguity.

## Evidence contract

A successful execution returns `status=sandbox_proof_passed` and records evidence containing:

- binding/task/adapter identities;
- operation class and exact scopes;
- grant reference;
- destination host and resolved-address count;
- HTTP status and content type;
- response SHA-256;
- request-body SHA-256 when a body was sent;
- canonical input SHA-256;
- Task Injection SHA-256 and schema version;
- evidence SHA-256;
- canonical output slot;
- completion timestamp;
- `network_request_executed=true`;
- `mapping_valid=true`;
- `ready_for_task_consumption=true`;
- `credential_material_included=false`;
- `raw_response_included=false`;
- `request_body_included_in_evidence=false`;
- `redirects_followed=false`;
- `production_allowed=false`;
- `runtime_connector_approved=false`.

The customer receives the canonical mapped input for the immediate proof response. Persistent evidence deliberately omits the canonical payload, raw customer response, outbound request body, and credentials; it retains their relevant digests and task/output identities instead.

## Supervisor grant lifecycle

Grants last from 5 to 120 minutes. Issuing a new grant for the same binding supersedes the previous active grant. Expired, missing, duplicated, task-mismatched, or operation-class-mismatched grants fail closed.

The client cannot self-grant live execution from Enterprise Settings. Grant issuance is under the existing admin integration-task readiness surface and requires a validated supervisor write session.

## Readiness meaning

A successful live sandbox proof means that Maestro has demonstrated, for that binding and task, that it can:

1. build the customer API request from canonical task inputs;
2. reach the declared sandbox API under network policy;
3. apply transient credentials without exposing them;
4. receive the expected API response;
5. transform the external response into the declared canonical task schema;
6. validate the result for the intended Maestro `task_id` and `output_slot`;
7. produce tamper-evident evidence linking request, response, mapping, grant, and task handoff.

This is the customer-facing operational proof of sandbox readiness for that configured binding. It does **not** mean production is enabled. Production remains a separate qualification decision with stronger credential, network, durability, and operational controls.
